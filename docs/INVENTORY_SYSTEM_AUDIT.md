# Inventory System Full Codebase Audit

## 1. Executive Summary

The system is a functional inventory MVP with a NestJS API, Prisma/PostgreSQL data model, Next.js frontend, JWT authentication, role/permission enforcement, location access checks, ledger-based stock movement, average costing, master-data import, opening inventory import, purchasing/receiving, transfers, store operations, reporting, and offline sync foundations.

Overall condition: the core architecture is coherent and the code shows good intent around validation, audit logging, immutable ledger events, and defensive role checks. The biggest risks are operational consistency and production hardening: several business flows create a source document first and then post ledger events in later service calls, which can leave partial documents if a later ledger post fails. Document numbers are generated by counting same-day rows, creating duplicate risks under concurrent use. Some detail/list routes can return cross-location data unless the service filters by the authenticated user's locations. Session handling is access-token-only, with logout not invalidating already issued tokens. File import endpoints accept buffered Excel uploads without explicit size/type limits.

This audit is based on code review only. No offensive testing, external scanning, or production probing was performed.

## 3. Process Flow Review

### Login / User Access

Current behavior:

- Public ALTCHA challenge: `AuthController.captchaChallenge()` at `apps/api/src/auth/auth.controller.ts`.
- Login: `AuthController.login()` calls `AuthService.login()`.
- Login verifies ALTCHA, finds user by email or username, checks active/restricted/locked status, validates bcrypt password, resets failed count, records audit, and returns a signed access token.
- JWT validation re-fetches user, role permissions, and location access in `JwtStrategy.validate()`.
- Admin user, role, permission, audit, offline PIN, and device routes are permission protected in `apps/api/src/admin/admin.controller.ts`.

Logic assessment:

- Good: password hashes use bcrypt, login failures are audited, account restriction/lock states exist, role permissions are loaded from the database on every request.
- Weak spot: `AuthService.refresh()` is deferred and `AuthService.logout()` only records audit. There is no token revocation, refresh-token rotation, session table, or forced logout capability.
- Weak spot: `defaultTemporaryPassword` is hardcoded in `apps/api/src/auth/password-policy.ts`. Even though users are forced to change it, this should not remain a shared known value for production.
- Weak spot: frontend stores access token in `localStorage` via `TOKEN_KEY` in `apps/web/lib/api-client.ts` and `AuthGate`. This is simple but exposes the token to any successful XSS.

Recommended improvements:

- Add refresh-token storage/rotation and a server-side session or token version table.
- On password reset/change, role change, deactivate, lock, or logout, invalidate existing sessions.
- Move temporary password generation to per-user random values.
- Consider httpOnly secure cookies or short-lived in-memory tokens plus refresh cookie.

### Item Setup

Current behavior:

- Item CRUD routes are in `MasterDataController` under `/api/admin/items`.
- DTOs validate SKU/name/type/base UOM/loose count fields in `apps/api/src/master-data/dto/master-data.dto.ts`.
- `MasterDataService.createItem()` and `updateItem()` validate active base UOM, category, and loose-count setup.
- Deactivation is soft via `active=false`.
- Bulk import is in `MasterDataImportService.importWorkbook()`.

Logic assessment:

- Good: base UOM and loose-count fields are validated; imports can update by stable SKU.
- Weak spot: changing an item's base UOM after ledger activity is not blocked in `MasterDataService.updateItem()`. This can reinterpret existing quantities and UOM conversions.
- Weak spot: import service writes rows sequentially and commits valid rows even if later rows fail. This is intentional per instructions but can leave partial imports.

Recommended improvements:

- Block base UOM changes once ledger, recipe, receiving, transfer, stock count, or supplier item records exist for an item.
- Add an import mode option: all-or-nothing validation first, then commit.

### Supplier Setup

Current behavior:

- Supplier CRUD is under `/api/admin/suppliers`.
- Supplier item CRUD is under `/api/admin/supplier-items`.
- `SupplierItem` supports supplier, item, brand, supplier SKU, pack size, purchase UOM, conversion to base, default unit cost, and active status.
- Purchasing uses supplier-item defaults in `PurchasingService.toPurchaseOrderLineCreateData()`.

Logic assessment:

- Good: supplier item mapping addresses the "same internal item, multiple suppliers/brands/SKUs" need.
- Weak spot: supplier-item uniqueness is only `@@unique([supplierId, itemId, supplierSku])`. PostgreSQL allows multiple rows when `supplierSku` is `NULL`, so the code adds application-level checks in `assertUniqueSupplierItem()`. Needs confirmation whether all import paths enforce equivalent uniqueness; `MasterDataImportService.findSupplierItem()` does a find-first for null SKU but concurrency can still duplicate.

Recommended improvements:

- Add database-level partial unique indexes for null supplier SKU if supported outside Prisma migrations.
- Require supplier SKU or brand+pack for supplier items used in purchasing if the business wants stricter selection.

### Warehouse / Branch Setup

Current behavior:

- Locations are `WAREHOUSE` or `BRANCH` in `LocationType`.
- Location CRUD is under `/api/admin/locations`.
- User access to locations is modeled by `UserLocationAccess`.
- `LocationAccessGuard` checks route body/query params when controllers declare `@LocationAccess`.

Logic assessment:

- Good: location access exists and is enforced on many create/list routes.
- Confirmed issue: detail routes often lack location access decorators and some service methods do not verify ownership after fetch. Examples:
  - `TransfersController.getTransfer()` and `getVariance()` call `TransfersService.getTransfer()` / `getVariance()` without checking user location access.
  - `PurchasingController.getPurchaseOrder()` and `getReceiving()` call `PurchasingService.list("purchase-orders.detail")` / `list("receivings.detail")` without user-based location checks.
  - `BranchOpsController.getStockCount()` returns by ID without user location check.

Recommended improvements:

- Pass `AuthenticatedUser` into all detail endpoints and verify returned record location(s) before response.
- For list routes, default to `user.locationIds` when no location filter is provided.

### Receiving / Stock-In

Current behavior:

- Receiving endpoint: `POST /api/purchasing/receivings` in `PurchasingController.receiveGoods()`.
- `PurchasingService.createReceiving()` validates supplier/location, validates PO status and remaining quantities when linked to a PO, creates a `Receiving`, creates ledger `RECEIVE` events, updates PO status, and audits.
- Purchase UOM to base conversion happens in `receivingLedgerCost()` and `purchaseQtyToBaseQty()`.

Logic assessment:

- Good: PO receiving does not automatically post stock until receiving is created; accepted quantity posts to ledger; rejected quantity does not.
- Good: accepted plus rejected quantity cannot exceed remaining PO quantity.
- Confirmed issue: standalone receiving without a PO posts `acceptedQty` directly as ledger base quantity. `CreateReceivingDto.ReceivingLineDto` has no `uomId`, so standalone receiving cannot declare purchase UOM or conversion. This can misstate stock if the entered quantity is not base UOM.
- Confirmed issue: document number generation uses same-day count in `nextDocumentNumber()`. Concurrent receipts can generate duplicate `RR-YYYYMMDD-####` values and fail one transaction.

Recommended improvements:

- Add `uomId` and optional supplier item to standalone receiving lines or require base UOM explicitly in UI/API.
- Replace count-based document numbering with a database sequence/counter table locked per prefix/day.

### Stock Transfer

Current behavior:

- Transfer routes are in `apps/api/src/transfers/transfers.controller.ts`.
- Create validates source/target location, unique items, active targets, available stock, and low-stock snapshots.
- Approve moves `DRAFT` to `APPROVED`.
- Dispatch records picked quantities and current average unit cost on transfer lines, but does not post ledger events.
- Receive posts both `TRANSFER_OUT` from source and `TRANSFER_IN` to target through `LedgerService.postEvent()`, updates received quantity, and handles variance review.

Logic assessment:

- Good: stock availability checks include reserved outbound quantities.
- Good: transfer-in requires a matching transfer-out event in `LedgerService.resolveUnitCostAtTime()`.
- Confirmed issue: `TransfersService.receiveTransfer()` posts ledger events before updating transfer lines/status. If posting succeeds but the later transfer update fails, the ledger can show completed movement while transfer remains dispatched.
- Confirmed issue: `TransfersService.dispatchTransfer()` validates source stock before transaction and then updates transfer line state in a separate transaction. Another concurrent dispatch/issue can consume stock between validation and update.
- Weak spot: dispatch does not post ledger events, so stock-on-hand uses reserved quantities as a derived display concept until receipt. This is workable but operationally important and should be clear in reports.

Recommended improvements:

- Move transfer receive ledger creation and transfer updates into one database transaction, using a transaction-scoped ledger posting helper.
- Lock affected stock rows or use a per-location/item inventory balance table for atomic reservations.
- Add a transfer event state model for dispatch reservations versus actual inventory movement.

### Stock-Out / Issuing

Current behavior:

- Issue to operations: `BranchOpsController.createIssueToOps()` -> `BranchOpsService.createIssueToOps()`.
- Lines are normalized to item base UOM via `normalizeQtyLines()` and `convertToBaseQty()`.
- `validateOutboundStock()` checks current stock minus reserved transfer quantities.
- Document is created and audited, then ledger `ISSUE_TO_OPS` events are posted.

Logic assessment:

- Good: negative stock prevention exists.
- Confirmed issue: document creation and ledger posting are not in the same transaction. If a ledger post fails after document creation, the issue document can exist without corresponding ledger movement.
- Confirmed issue: outbound stock validation is outside the document transaction and before ledger posting; concurrent stock-out can still race.

Recommended improvements:

- Use one transaction for document creation and ledger events.
- Add idempotency keys or unique document-source fields for repeated submissions.

### Stock Adjustment

Current behavior:

- Adjustment requests are created in `LedgerService.createAdjustmentRequest()`.
- Reason code must be active and type `ADJUSTMENT`.
- Outbound adjustments are checked against current stock.
- Approval posts a ledger `ADJUSTMENT` event and then updates the request to `POSTED`.

Logic assessment:

- Good: adjustment has a request/approve/reject workflow and audit trail.
- Confirmed issue: `approveAdjustmentRequest()` calls `postEvent()` first and then updates the request in a second transaction. If the request update fails after ledger posting, the ledger event remains while the request can still look pending.
- Weak spot: approver can be the same user as requester; no segregation-of-duties rule is visible.

Recommended improvements:

- Post the ledger event and mark the request posted in one transaction.
- Add an optional rule preventing requester self-approval for production.

### Stock Count / Physical Count

Current behavior:

- Store stock counts are posted through `BranchOpsService.submitStockCount()`.
- Store Operations supports `OPENING` and `EOD` only via `validateStoreCountType()`.
- System quantity is calculated from ledger events, variance is recorded, and variance posts ledger `STOCK_COUNT` events.
- Opening inventory upload uses `OpeningInventoryImportService.importWorkbook()`, blocks upload if the selected location already has ledger movement, creates a posted stock count and ledger entries in one transaction.

Logic assessment:

- Good: opening inventory is guarded so it can only seed a location with no movements.
- Good: loose count is supported for configured items.
- Confirmed issue: branch stock count document creation is separate from later ledger posting. Partial posting is possible if a ledger event fails after stock count creation.
- Weak spot: no duplicate count prevention per location/business date/count type is visible.
- Weak spot: `OpeningInventoryImportService.resolveUnitCost()` silently uses zero cost if an invalid unit cost is supplied instead of adding a row error.

Recommended improvements:

- Add unique or business-rule checks for one opening count per location and controlled EOD count frequency.
- Treat invalid unit cost as an import error.
- Make stock count document and ledger variance postings atomic.

### Spoilage / Wastage

Current behavior:

- Wastage routes are in `BranchOpsController`.
- `BranchOpsService.createWastage()` validates location, unique items, WASTAGE reason code, stock availability, creates wastage document, audits, then posts `WASTAGE` ledger events.

Logic assessment:

- Good: wastage requires reason code and stock check.
- Confirmed issue: same two-step document then ledger pattern creates partial-post risk.
- Weak spot: `photoUrl` exists in schema but the DTO/controller does not expose upload or capture.

Recommended improvements:

- Make wastage document and ledger events atomic.
- Add photo/file handling with safe upload limits if evidence capture is required.

### Purchase Request / Purchase Order

Current behavior:

- Purchase orders support create, update, submit, approve, reject, close balance.
- Cost override reason is required when line cost differs from supplier default.
- Approving a PO approves override metadata.
- POs do not affect stock until receiving.

Logic assessment:

- Good: PO workflow state checks are present.
- Good: PO receiving computes remaining quantity from previous receivings.
- Confirmed issue: there is no separate purchase request module; purchase order starts the process.
- Confirmed issue: PO line validation does not enforce that a selected `uomId` matches supplier item purchase UOM or converts to item base UOM at PO creation. Conversion failure may surface later at receiving.

Recommended improvements:

- Add purchase request if client process requires pre-PO request/approval.
- Validate PO line UOM against supplier item purchase UOM or item base UOM at creation time.

### Reporting

Current behavior:

- Reports are CSV-only in `ReportsService`.
- Report runs are persisted in `report_runs`.
- Stock, valuation, movements, wastage summary, transfer variance, and low-stock reports exist.
- Access is filtered by `locationIds` in report parameters.

Logic assessment:

- Good: users can only read report runs whose stored `locationIds` are all within their access.
- Weak spot: report output is regenerated on download, not stored. Historical report download can change if data changes after run completion.
- Weak spot: report calculations use JavaScript `number` in `stockRows()`, unlike ledger/costing services that use `Prisma.Decimal`. This can introduce rounding drift.
- Weak spot: `runReport()` ignores requested `format` except requiring CSV in DTO.

Recommended improvements:

- Persist report output or an immutable snapshot at run time.
- Use `Prisma.Decimal` consistently for stock valuation.
- Either remove unsupported report formats from model/UI or implement XLSX/PDF.

### Audit Logging

Current behavior:

- `AuditService.record()` writes module/action/entity/before/after/user/location/IP/user-agent.
- CRUD and workflow services write audit entries in many paths.
- Audit log search is exposed via admin.

Logic assessment:

- Good: audit log design is broad and captures before/after for many master-data changes.
- Confirmed issue: failed/partial workflow attempts may not be fully auditable where document creation and ledger posting are split.
- Confirmed issue: demo reset scripts clear audit logs.

Recommended improvements:

- Preserve audit logs in production resets or archive them separately.
- Record failed workflow attempts in high-risk posting flows.

## 4. Security Review

### Critical

No confirmed critical code issue was found in this defensive code review.

### High

1. Access tokens cannot be revoked.
   - Files/functions: `AuthService.refresh()` and `AuthService.logout()` in `apps/api/src/auth/auth.service.ts`; frontend token storage in `apps/web/components/auth-gate.tsx`.
   - Risk: a stolen or old access token remains valid until expiry; logout does not invalidate it.
   - Action: implement session/refresh-token persistence, revocation, token versioning, and forced logout on account changes.

2. Detail endpoints can expose records outside caller location access.
   - Files/functions: `TransfersController.getTransfer()`, `TransfersController.getVariance()`, `PurchasingController.getPurchaseOrder()`, `PurchasingController.getReceiving()`, `BranchOpsController.getStockCount()`.
   - Risk: a user with read permission can fetch known UUIDs for records outside assigned locations.
   - Action: pass `CurrentUser` into detail endpoints and verify location access in service response.

3. Multi-step posting flows can leave source documents and ledger events inconsistent.
   - Files/functions: `BranchOpsService.createWastage()`, `submitStockCount()`, `createIssueToOps()`, `createEmergencyPurchase()`, `createSalesBatch()`, `TransfersService.receiveTransfer()`, `LedgerService.approveAdjustmentRequest()`.
   - Risk: failed second step creates partial business records or orphaned ledger movements.
   - Action: refactor to transaction-scoped posting helpers and commit document plus ledger atomically.

### Medium

1. File uploads lack explicit size/type limits.
   - Files/functions: `MasterDataController.importMasterData()` and `LedgerController.importOpeningInventory()` use `FileInterceptor("file")`.
   - Risk: memory pressure or malformed/large file denial of service.
   - Action: configure multer limits, MIME/extension checks, and import row count caps.

2. Count-based document numbering is race-prone.
   - Files/functions: `PurchasingService.nextDocumentNumber()`, `TransfersService.nextTransferNumber()`, `BranchOpsService.nextDocumentNumber()`, `LedgerService.nextAdjustmentRequestNumber()`, `OpeningInventoryImportService.nextStockCountNumber()`.
   - Risk: concurrent requests can generate the same document number and fail one transaction.
   - Action: use a database sequence or locked counter table.

3. Shared temporary password exists in code.
   - File: `apps/api/src/auth/password-policy.ts`.
   - Risk: predictable credential during user provisioning or reset.
   - Action: generate random temporary passwords and require change.

4. Frontend stores JWT in `localStorage`.
   - Files/functions: `TOKEN_KEY` in `apps/web/lib/api-client.ts`; `AuthGate.login()`.
   - Risk: XSS can exfiltrate token.
   - Action: consider httpOnly secure cookies or in-memory token storage with refresh cookie.

5. Public password reset endpoints are placeholder responses.
   - File/functions: `AuthController.requestPasswordReset()` and `confirmPasswordReset()`.
   - Risk: UX and operational confusion; clients may assume reset is functional.
   - Action: hide endpoints until implemented or implement a secure reset workflow.

### Low

1. Security headers are basic and CSP is API-focused.
   - File: `apps/api/src/main.ts`.
   - Risk: frontend protection is mostly outside API headers.
   - Action: define Next.js security headers for the web app too.

2. Login form defaults identifier to `admin`.
   - File: `apps/web/components/auth-gate.tsx`.
   - Risk: makes the admin username obvious.
   - Action: use an empty identifier in production.

## 5. Database and Data Integrity Review

Strengths:

- Prisma schema defines foreign keys and many useful indexes.
- Ledger events are UUID-idempotent and use decimal quantities/cost.
- Stock is derived from ledger events, reducing direct balance mutation risks.
- Role-permission and user-location access models are clear.

Confirmed issues and risks:

- `SupplierItem` uniqueness with nullable `supplierSku` can allow duplicate null-SKU supplier items at the database level. File: `apps/api/prisma/schema.prisma`, model `SupplierItem`.
- No database uniqueness for one stock count per location/date/type. File: model `StockCount`.
- No database uniqueness for external receiving references by supplier/location/invoice/DR. File: model `Receiving`.
- Business document numbers are unique but generated with same-day count, creating concurrency collisions.
- Item base UOM can be changed after transactions unless blocked in service code. File/function: `MasterDataService.updateItem()`.
- Audit logs are not immutable at the database level and are cleared by reset scripts.
- `ReportRun` has `requestedById` but no relation to `User` in Prisma schema, so referential integrity is not enforced.

## 7. Robustness and Operations Review

Confirmed strengths:

- Production startup requires `JWT_ACCESS_SECRET` and `ALTCHA_HMAC_SECRET` in auth code.
- Global validation pipe uses whitelist, forbid non-whitelisted, and transform in `apps/api/src/main.ts`.
- Reset helpers create backups and guard against production-looking DBs in `scripts/db-reset-helpers.js`.
- Docker images include generated Prisma client and build steps.

Confirmed risks:

- `docker-compose.yml` contains local development credentials. This is acceptable for local, but must not be used as production configuration.
- API rate limiting in `apps/api/src/main.ts` is in-memory. It resets on restart and does not coordinate across replicas.
- `MasterDataImportService.importWorkbook()` and `OpeningInventoryImportService.importWorkbook()` buffer and process entire workbooks.
- Full workflow rollback/recovery is not implemented for partial document/ledger posting.
- Report output is regenerated at download instead of stored.
- `SalesService` is a placeholder, while branch sales batches are implemented separately in `BranchOpsService.createSalesBatch()`. Needs client-facing clarity.
